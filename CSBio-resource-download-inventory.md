An unknown setting means it is not publicly visible, not that it does not exist.

## Delivery requirement confirmed after the audit

The user confirmed that the current practical-guide email contains a PDF attachment and that the replacement must not expose a reusable public PDF link. The earlier recommendation to upload a Public - noindex file and link to it does not meet this requirement. Noindex is not access control.

Keep the HubSpot form and CRM property work. Delivery needs a revised design: an attachment-capable email integration would preserve the existing attachment experience without publishing a reusable file link. A recipient-authenticated download service is a separate option if access must be checked for each reader. Neither approach prevents someone from forwarding a PDF after receiving or downloading it. The delivery integration has not been selected or implemented.

The user has prepared a practical-guide form, uploaded its PDF to HubSpot, and drafted a delivery email. They reported lacking permission to activate its workflow and asked to pause activation. Their later screenshot shows the uploaded file set to Private. The draft email's former public download link must be replaced with the chosen delivery design before launch.

### Popup loading investigation

- The unmodified HubSpot embed also stays blank on a plain local HTTP test page, outside the website and popup.
- A local control iframe on that page loads successfully. Both an explicitly HTTPS HubSpot share-page iframe and an HTTPS CSBio-page iframe stay blank, without emitting their load events. This narrows the failure to external frames in the local in-app preview; it is not limited to the HubSpot embed or popup styling.
- The existing 123FormBuilder popup on the live HTTPS Practical Guide page loads successfully in the same in-app browser.
- The HubSpot share page and CSBio control page both return HTTP 200 and do not return X-Frame-Options or Content-Security-Policy headers in the inspected responses.
- An HTTP-to-HTTPS redirect was observed for HubSpot's generated iframe URL, but the explicit HTTPS control also fails. That redirect alone has not been established as the cause.
- The user authorized a Chrome comparison. Browser tooling reports Chrome is not connected, so the user opened the same local preview in Chrome and confirmed that the HubSpot form appears inside the restored popup.

Conclusion: the popup and supplied HubSpot embed render in Chrome. The blank external frames are specific to the in-app browser's local preview in these tests; its internal cause has not been determined. The website retains the popup, with the standalone request-form link only as a fallback. This verifies form display only; submission and PDF delivery are still untested.
